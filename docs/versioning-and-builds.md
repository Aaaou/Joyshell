# Joyshell 版本与构建编号规则

生效范围：从 `0.1.69_build_2` 开始的所有可分发版本。`build_2` 为未分发的内部候选，后续修复构建按序递增；当前正式收口构建为 `build_4`。

## 版本标识

Joyshell 使用功能版本和构建序号共同标识一个可分发产物：

- 功能版本保持三段数字，例如 `0.1.70`。
- 展示标识使用 `<功能版本>_build_<序号>`，例如 `0.1.70_build_1`。
- Git 标签使用与其等价且兼容常见版本工具的 `v<功能版本>-build.<序号>`，例如 `v0.1.70-build.1`。
- Windows EXE/MSI 产品版本继续使用三段或四段纯数字版本；`build` 序号通过界面标识、Release 标题、Git 标签和产物文件名体现。

## 递增规则

1. 每次生成准备交付给测试者或用户的安装包、便携包或其他可分发构建，当前功能版本的 `build` 序号必须加一。
2. 同一功能版本首次对外构建从 `build_1` 开始，随后为 `build_2`、`build_3`，不得回退或复用。
3. 本地调试和未交付的普通开发编译不消耗构建序号；一旦产物被上传、发送或写入发布报告，就视为已使用。
4. 任何源码、资源、依赖、安装脚本、签名或打包配置发生变化后重新出包，都必须使用新的 `build` 序号。
5. 已发布的 Git 标签、Release 资产和 SHA-256 不得被同名替换。需要修复时创建下一个 `build`。
6. 功能版本升级时，构建序号从 `build_1` 重新开始，例如从 `0.1.70_build_4` 进入 `0.1.71_build_1`。

## 发布产物

从 `0.1.69_build_2` 开始，产物命名应包含完整展示标识，例如当前正式发布：

```text
Joyshell_0.1.69_build_4_x64-setup.exe
Joyshell_0.1.69_build_4_x64_en-US.msi
```

Release 标题、发布报告、应用内版本标识、安装包文件名和 SHA-256 清单必须指向同一个构建。发布报告至少记录：

- 功能版本和 `build` 序号。
- 对应 Git 提交和 Git 标签。
- 构建时间、目标平台和发布类型。
- 自动测试及实机验收结果。
- 每个发布产物的 SHA-256 和签名状态。

## 当前过渡

已发布的无构建号 `v0.1.69` 视为 `0.1.69` 功能版本的历史首次分发构建，但不追改标签、资产名或哈希。企业网络稳定性修复包使用 `0.1.69_build_3`、标签 `v0.1.69-build.3`；已出包但未分发的 `build_2` 不复用。旧 Release 只标记为已被替代，不覆盖或删除原资产。本次正式收口包为 `0.1.69_build_4`；进入 `0.1.70` 时从 `0.1.70_build_1` 重新开始。
